Steward Insight: Reviews and Diaries → experiences/
=====================================================

SUMMARY
-------
Reviews generated by semantic_reviewer (e.g., pulselab_zero.json) contain
critical issues, proposals, and a final circuit snapshot. These artifacts
belong in `validation_complex/runs/...` — they are **not** automatically
promoted to the `experiences/` knowledge base.

The current pipeline has no explicit step that:
  • checks if a run is marked as *passed* or *approved*, and
  • extracts lessons, placement rules, critical nets, gerber path, etc.,
    from the review result to build a `DesignExperience` record.

Without this bridge, validated designs stay isolated in the validation runs
directory and never become reusable knowledge entries. This means:
  – The RAG system cannot query past validations.
  – Lessons learned remain siloed.
  – Future designs cannot benefit from previous validation findings.

FINDINGS
--------
1. `design_experience.py` defines `DesignExperience` and provides helpers
   (`record_design_outcome`) to persist a design outcome into
   `experiences/`. It expects fields like `board_id`, `timestamp`,
   `mcu`, `layer_count`, `drc_violations`, `routing_success_rate`,
   `manufacturing_target`, `lessons_learned`, `component_placement_rules`,
   `critical_nets`, `gerber_path`, and a boolean `passed`.

2. Validation runs produce JSON files (e.g., `pulselab_zero.json`) that
   contain:
   – `run_session` identifier,
   – `semantic_review` with issues and proposals,
   – final circuit netlist,
   – pin coverage metrics,
   – variant (`ab_variant`).

3. The `experiences/` directory is populated only when a design is
   explicitly recorded as an experience — typically after a full PCB
   validation run (DRC + routing checks) has been completed and the
   result marked as passed.

4. There is no documented code path that takes a semantic review result
   and converts it into a `DesignExperience`. The `ingest_to_rag()` method
   exists on `DesignExperience`, but the data must first be instantiated
   with appropriate fields before calling `save()`.

5. Review markdown files (`review.md`) are human-readable summaries of
   the same semantic review — they also do not become experiences.

PROPOSALS / RECOMMENDATIONS
---------------------------
A. Add a new method to `design_experience.py` called
   `from_validation_run(path)` (or similar) that:
   – Loads the JSON from a validation run,
   – Extracts relevant fields:
     * board_id = run_session or a derived name,
     * mcu = MCU value from the circuit,
     * layer_count = derived from Gerber export (if available),
     * drc_violations = count of issues with severity "critical",
     * routing_success_rate = 1.0 if no critical issues else computed metric,
     * manufacturing_target = default or parsed from metadata,
     * lessons_learned = list of proposal strings from semantic_review,
     * component_placement_rules = (empty by default unless parsed),
     * critical_nets = nets associated with critical issues,
     * gerber_path = path to exported Gerbers if present,
     * passed = boolean flag indicating whether the run was approved,
   – Instantiates `DesignExperience` and calls `save()` into `experiences/`.

B. Create a companion method `from_review_md(path)` that parses a
   markdown review file (e.g., `review.md`) to extract issue summaries
   and proposals, then builds the same `DesignExperience` record. This
   allows older runs that only have markdown reviews to be imported.

C. Wire up an entry point in the validation pipeline (e.g., after
   `semantic_review` completes) to call either of these methods based on
   the run's metadata (`run_session`, `ab_variant`, etc.). Ensure that
   the resulting `DesignExperience` is only written if the run is marked
   as passed — otherwise it could pollute the experiences directory with
   failed designs.

D. Consider adding a configuration flag (e.g., in `config.yaml`) to
   control whether validation runs should auto-promote to experiences,
   or require explicit approval. This gives operators flexibility.

E. Document this process in the project docs under `docs/status/`
   so future maintainers understand why validation artifacts exist
   alongside experiences.

IMPLEMENTATION NOTES
--------------------
- The existing `record_design_outcome()` helper already handles creating,
  saving, and ingesting into RAG — it can be reused once we populate
  the fields from a validation run.
- When extracting `drc_violations`, treat any issue marked "critical" as
  a DRC violation; warnings could be aggregated separately if desired.
- For `routing_success_rate`, a simple heuristic: start at 1.0 and reduce
  by a factor per critical issue (e.g., 0.95 per issue) — or compute a
  more precise metric if routing data is available.
- The `ingest_to_rag()` method expects `lessons_learned` and
  `component_placement_rules` lists; ensure we pass them correctly.

CONCLUSION
----------
Currently, semantic reviews are not automatically added to the
`experiences/` knowledge base. To bridge this gap, we need to introduce
new methods in `design_experience.py` that can ingest validation run
JSON (or markdown review) files and create proper `DesignExperience`
records. This ensures that validated designs become reusable knowledge,
feeding both the local experiences directory and the RAG system for
future retrieval.
